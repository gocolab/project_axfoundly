### BAT-001. LMS 당일 명단·출결 폴링

- **목적**: LMS 출결 API에서 당일 입실자 명단·출결 데이터를 주기적으로 가져와 우리 DB(`daily_roster`)에 적재한다. 대시보드·판정·알림은 LMS를 직접 조회하지 않고 **항상 이 컬렉션만 본다** (LMS 장애 시에도 마지막 동기화 상태로 화면 유지)
- **실행 주기**: `fixedDelay = 60초` 상시 실행 + 내부 시간대 가드 — 매 tick마다 현재 시각으로 LMS 호출 여부 결정. **시간대 경계는 고정값이 아니라 아래 "퇴실 시각 도출 규칙"으로 강의별 시각에서 계산한 합집합**:

  | 시간대 (Asia/Seoul, 평일) | LMS 호출 | 이유 |
  |---|---|---|
  | 입실 창 = ∪[강의 시작 −60분, +60분] | 5분에 1회 | 대시보드 갱신. 입실은 판정 시한(BAT-002 09:30)까지 여유가 있어 분 단위 신선도 불필요 |
  | 퇴실 창 = ∪[강의 종료 −30분, +60분] | 매 tick (1분) | `checkedOut` 갱신이 "퇴실 미체크(DB 잔존)" 판정·카메라 포착 플로우의 기준 데이터 — 여기만 분 단위 신선도가 필요 |
  | 그 외 (주간 유휴) | 10분에 1회 | 늦은 태그 반영 (실측: 종료 3시간 뒤 퇴실 태그 사례 존재) |
  | 심야(마지막 퇴실 창 종료 ~ 첫 입실 창 시작)·주말 | 호출 안 함 | 데이터 변동 없음 |

- **실행 시간대 기준**: Asia/Seoul
- **상태**: ✅ 구현 완료 (2026-08-09 — 처리 1~9 / 2026-08-11 — `period` 화이트리스트·`daily_courses.period_end_date` 저장)

    `adapter/out/lms`(수집·변환) · `adapter/out/persistence`(적재)

#### 퇴실 시각 도출 규칙 (2026-08-07 CTO 확정)

수업 운영은 **오전반·오후반·야간반 3틀**이지만, **실제 퇴실 시각은 강의마다 다르다** — 배치 트리거를 3개 고정 시각으로 두면 어긋나는 강의가 생긴다 (2026-08-07 실측 근거 아래).

- **규칙: 강의별 퇴실 시각 `T_out`은 LMS `time` 필드의 종료 시각을 파싱해 사용한다** (예: `"09:20~18:10(총 8시간)"` → `18:10`). 입실 시각 `T_in`도 같은 방식으로 시작 시각을 파싱
- **반 구분은 `T_out`을 버킷팅해 표시용으로만 사용**: `~15:00` = 오전반 / `~20:00` = 오후반 / 그 이후 = 야간반. 판정·트리거는 언제나 강의별 `T_out` 기준
- **파싱 실패 시**: 해당 강의는 폴백 퇴실 시각(`LMS_DEFAULT_CHECKOUT_TIME`, 기본 18:00) 적용 + WARN 로그 — 형식이 바뀌어도 배치가 멈추지 않게 한다
- **`classDay=false`인 강의는 창 계산에서 제외한다** (2026-08-07 추가). 전 강의가 `false`면 합집합이 비고, 그러면 그날은 카메라도 배치 실호출도 돌지 않는다 — 공휴일·휴강 판단을 우리가 달력으로 관리하지 않고 LMS가 알려주는 대로 따른다는 뜻이다
  - 이 규칙이 생기면서 `DETECTION_WEEKDAYS_ONLY`(요일 하드코딩)는 **2차 방어선**이 된다. LMS가 응답하지 못한 날에도 주말이면 안 돌게 하는 용도로만 남긴다
- **카메라 탐지 창은 퇴실 창과 동일한 합집합**을 쓴다 (`.env` `DETECTION_WINDOW` — 다중 구간 지원 필요, webapp 구현 대상)

**2026-08-07 실측 (전 강의 6개)** — 3틀 고정 시각이 맞지 않는 근거:

| 강의 | LMS `time` | `T_out` | 반 버킷 | 실제 퇴실 태그 범위 |
|---|---|---|---|---|
| 자격증+사무행정실무 | 09:30~13:30 | **13:30** | 오전 | 12:23~13:25 |
| 컴퓨터활용능력2급 | 09:00~14:00 | **14:00** | 오전 | 13:50~13:54 |
| RAG·LLM·BPM 로우코드 | 09:10~18:00 | **18:00** | 오후 | 13:01~17:59 |
| 심화_AI 지능형 솔루션 (우리 과정) | 09:20~18:10 | **18:10** | 오후 | 18:01~18:20 |
| 일반기계기사 취득과정A | 09:20~18:10 | **18:10** | 오후 | 18:00~**21:04** |
| 회사에서 쓰는 엑셀실무 | 19:00~22:00 | **22:00** | 야간 | 21:52~21:53 |

- 퇴실 시각이 **5종**(13:30·14:00·18:00·18:10·22:00) — 13:00/18:00/22:00 고정 트리거였다면 사무행정(13:30)은 수업 중 판정, 컴활2급(14:00)은 4시간 지연, 우리 과정(18:10)은 10분 조기 판정
- 퇴실 태그는 `T_out` **직전 30분~직후**에 몰린다 → 퇴실 창을 `[T_out−30, T_out+60]`으로 잡는 근거
- 종료 3시간 뒤(21:04) 퇴실 태그 사례 존재 → **창 밖 지각 태그는 유휴 10분 폴링이 흡수** (최대 10분 내 반영)

**오늘 시간표 기준 계산 예시** (합집합 — 강의 시간표가 바뀌면 자동으로 달라짐):
- 입실 창: `08:00~10:30`, `18:00~20:00`
- 퇴실 창 = 카메라 탐지 창: `13:00~15:00`, `17:30~19:10`, `21:30~23:00`

- ⚠ 이 API는 인증 없이 공개 인터넷에 노출되어 있고 이름·생년월일을 포함한다 — 학원 측에 공유 예정. 우리 쪽 방어: URL 비커밋 + `birth` 미열람 + 입실자만 저장

##### 조기취업자 — 미출석 집계를 LMS 값으로 쓰는 이유 (2026-08-07 CTO 확정)

실응답에 `status="조기취업"`인 수강생이 있다. `checkInTime`이 null이라 **우리 도메인은 미출석으로 센다**. 그런데 LMS의 강의 레벨 `absent`에는 포함되지 않는다 — 한 강의가 `total 7 = present 5 + absent 1 + earlyEmployed 1`로 나뉜다.

- 우리가 직접 세면 미출석 5명, LMS `absent` 합계는 4명 — **조기취업자 1명만큼 어긋난다**
- 개인 `status`를 읽으면 구분되지만 화이트리스트 제외 필드다 (읽지 않기로 한 결정 유지)
- **결론: `daily_stats.absent_count`는 강의 레벨 `absent`의 합을 쓴다.** 강의 레벨 집계는 개인정보가 아니라 화이트리스트 원칙과 충돌하지 않고, 개인 필드를 읽지 않고도 정확해진다
- 명단(`daily_roster`) 쪽은 영향 없음 — 조기취업자도 `checkInTime`이 null이라 어차피 저장되지 않는다

2. 경계면 네이밍 변환 (rules/09): 위 매핑표의 화이트리스트 필드만 snake_case로 추출 — `checkInTime`은 HHmm 문자열→시각 변환 포함
3. `daily_courses`에 **멱등 upsert** — 키 `(course_id, date)`. `time` 파싱으로 `class_start_time`·`class_end_time` 저장 (퇴실 창·BAT-003의 기준) + `classDay` 저장
4. **입실자 선별**: `checkInTime`이 있는 attendee만 대상으로 삼는다. **미출석자는 저장하지 않는다** (rules/04 행 최소화 — 결석자 개인정보를 우리 DB에 남기지 않는다)
5. 선별된 입실자를 `daily_roster`에 **멱등 upsert** — 키 `(student_id, date)`. 같은 데이터를 몇 번 받아도 결과 동일 (재시도·중복 호출 안전)
6. 퇴실 태그(`checkedOut=true`) 확인된 학생은 **개인정보 즉각 삭제** 원칙(rules/04) 적용 — roster 문서 삭제(TTL 인덱스는 백스톱). **roster에서 사라지는 것 자체가 "관리 대상 제외"** — 별도 제외 플래그를 두지 않는다
   - 이때 `checkoutStatus="조퇴"`면 삭제 전에 **EARLY_LEAVE 예외를 자동 등록**한다 (`source=LMS_AUTO` — BAT-003·API-005 참조). 제외는 이미 roster 삭제로 이뤄지므로, 자동 등록의 목적은 **대시보드 가시성·판정 근거 추적**이다
7. 정합성 검증 — **LMS 집계 ↔ 우리 계산을 4쌍 비교**한다. 불일치 시 WARN 로그 + 대시보드 경고 (수집 누락·API 이상 감지, 강사 요구 "데이터 수신 증명" 대응)

   | LMS 집계 | 우리 계산 | 이 비교가 잡아내는 것 |
   |---|---|---|
   | `total` | `attendees.length` | 응답 자체의 누락 |
   | `present` + `late` | `checkInTime`이 있는 수 | 입실 판정이 LMS와 어긋남 |
   | `checkedOut` | `checkedOut=true`인 수 | 삭제 대상 산정 오류 |
   | `notCheckedOut` | 입실 − 퇴실 (= 우리 관리 대상 수) | **명단 잔존 수가 실제와 다름** — 문자 오발송과 직결 |

   - `earlyLeave` ↔ 우리가 센 `checkoutStatus="조퇴"` 수도 함께 비교 (EARLY_LEAVE 자동 등록 누락 감지)
   - 2026-08-07 실응답 기준 5쌍 전부 일치 확인 — 이 검증은 "LMS가 틀렸나"가 아니라 **"우리 파이프라인이 제대로 세고 있나"** 를 매 tick 확인하는 장치다
   - **`capacity` ↔ 우리 roster 수 비교는 하지 않는다** — 결석자만큼 차이 나는 것이 정상
8. 익명 집계 갱신: `daily_stats`에 입실·미퇴실·퇴실·미출석 **수치만** 기록 (미출석자 개인정보는 저장하지 않음). `absent_count`는 강의 레벨 `absent`의 합 — 위 "조기취업자" 항목 참조
9. 변경 발생 시 WebSocket(API-008)으로 대시보드 갱신 이벤트 발행

> **출석 판정은 이진** — `check_in_time` 존재 = 출석, 부재 = 미출석 (지각·유예 분류 없음. 공식 판정은 LMS 소관, 우리는 보조 시스템 — 99_DECISIONS 2026-08-06). 이 원칙 때문에 미출석자를 저장할 필요가 없다: "저장돼 있지 않다 = 미출석"이 곧 판정이다

#### 실패 / 예외 처리

- **재시도**: 별도 즉시 재시도 없음 — 다음 tick(1분 후)이 재시도 역할
- **부분 실패 시**: 실패 건만 WARN 기록 후 계속 (전체 롤백 없음 — upsert 멱등이라 다음 tick에 자연 복구)
- **중복 실행 방지**: `fixedDelay`는 이전 실행 종료 후 대기라 겹침 없음. 단일 인스턴스 전제
- **알림**: LMS 호출 **연속 5회 실패 시 경고 1회** (채널 ❓ 미결정 — 0장 공통 규칙 따름) + 대시보드 상단 배너 ("LMS 연동 이상 — 마지막 동기화 HH:mm"). 복구 시 복구 알림 1회

#### 실행 이력 기록
- `batch_runs`에 tick별 기록은 과다 — **LMS 실호출 시에만** 기록 (시각·성공 여부·upsert 건수·정합성 결과)

#### 호출량 관리 (2026-08-07 CTO 확정 — rate limit 대응)

LMS 담당자가 공식 상한을 명시하지 않았으므로, **우리가 스스로 상한을 지키는 설계**로 간다.

- **응답이 전 강의 통합 스냅샷**이라 강의가 몇 개든 **호출 1회로 전부 커버**된다 — 강의별 개별 호출 없음
- 위 주기 기준 평일 예상 호출량 **≈ 400회/일** (퇴실 창 1분 ≈ 310 + 유휴 10분 ≈ 30 + 입실 창 5분 ≈ 55). 주말·심야 0회
- 모든 주기·창은 설정값이라 학원 요청 시 **코드 수정 없이 낮출 수 있다**
- **오발송 방지의 최종 안전장치는 폴링 주기가 아니라 "문자 발송 직전 최종 확인"**(rules/05 안전장치): 카메라 포착 → 문자 발송 직전에 LMS 1회 재조회로 퇴실 여부 최종 확인 후 발송. 문자는 하루 몇 건이라 호출 부담이 없고, **폴링이 늦어도 정상 퇴실자에게 복귀 문자가 나가는 사고를 원천 차단**한다
- ⚠ **"퇴실 1시간 전 최종 수신 후 폴링 중단"은 채택하지 않음** — 실측상 정상 퇴실 태그가 `T_out` 이후에 찍히므로(18:00~18:20, 늦게는 21:04), 그 시점에 폴링을 멈추면 정상 퇴실자를 "미퇴실"로 오판해 문자를 보내게 된다. 대신 `T_out−60`은 **관리 대상 확정 시점**으로 사용한다 (BAT-003)

#### 비고
- 시간대 경계·주기는 하드코딩하지 않고 설정으로: `application.yml` + `.env` (`LMS_POLL_INTERVAL_CHECKOUT=1m`, `LMS_POLL_INTERVAL_CHECKIN=5m`, `LMS_POLL_INTERVAL_IDLE=10m`, `LMS_DEFAULT_CHECKOUT_TIME=18:00`) — 구현 시 `.env.example` 갱신 필수. **창 경계 자체는 설정이 아니라 LMS `time` 파싱 결과**(퇴실 시각 도출 규칙)
- 출석 인정 마감(현재 유예 포함 09:30)은 판정 분류가 아니라 **BAT-002의 트리거 시각 설정값**으로만 사용
- ✅ **연락처(`phone`) 확보 방식 (2026-08-07 LMS 담당자 확인)**: 현재 응답에 연락처가 없다. **개발 단계에서는 팀원 연락처를 테스트 수신처로 사용하고, 시스템 완성 후 LMS가 API 응답에 학생 연락처를 추가해 준다.**
  - BAT-001은 지금은 `phone`을 매핑하지 않는다 (`daily_roster.phone`은 항상 null). LMS가 필드를 추가하면 화이트리스트에 한 줄 더하면 된다
  - 실발송 전환은 `SMS_MODE` 스위치로만 — 기본값 `test`(팀원 번호로 강제 치환). rules/05 안전장치 참조
- ⬜ 미확정 (잔여 1건):
  - `lunchMinutes`·`checkoutGraceMin` 필드가 응답에 있으나 전 강의 `null` — 이름상 퇴실 유예 시간을 제공할 의도로 보인다. 값이 채워지면 퇴실 창 계산에 반영 검토

### BAT-003. 퇴실 관리 대상 확정

- **목적**: 강의별 퇴실 1시간 전에 "오늘 이 강의에서 퇴실을 찍어야 하는 사람"을 확정하고, 그 전에 이미 나간 사람(조퇴)을 관리 대상에서 정리한다. 퇴실 시간대 카메라 감시·문자 플로우가 **누구를 대상으로 도는지**를 명확히 하는 기준점 (2026-08-07 CTO 결정)
- **실행 주기**: `fixedDelay = 60초` + 시간대 가드 — 매 tick마다 "현재 시각 == 어떤 강의의 `T_out − 60분`"인지 확인해 해당 강의만 처리. **고정 cron이 아닌 이유는 `T_out`이 강의마다 다르기 때문** (퇴실 시각 도출 규칙 참조)
  - 오늘 시간표 기준 실행 시점 예시: 12:30(사무행정) · 13:00(컴활2급) · 17:00(RAG·LLM) · 17:10(심화_AI·기계기사) · 21:00(엑셀실무)
- **실행 시간대 기준**: Asia/Seoul
- **상태**: 📝 설계

#### 처리 내용

1. LMS 폴링 1회 강제 실행 (BAT-001 로직 재사용) — 확정 직전 최신 상태 확보
2. 해당 강의의 당일 명단에서 **관리 대상 확정**: `daily_roster`에 잔존(= 아직 퇴실 미체크)하고 당일 예외가 없는 학생
3. **조기 퇴실자 정리**: 이 시점에 이미 `checkedOut=true`인 학생
   - `checkoutStatus="조퇴"` → `attendance_exceptions`에 **EARLY_LEAVE 자동 등록** (`source=LMS_AUTO`, `start_time`=`checkOutTime` 변환값)
   - 정상 `퇴실` → 예외 등록 없이 통과 (정시 전 퇴실 태그일 뿐)
   - 어느 쪽이든 roster에서는 이미 삭제된 상태 = **관리 대상 자연 제외** (BAT-001 처리 내용 5)
4. 확정 결과를 `batch_runs`에 기록. 화면 갱신은 처리 1의 사전 폴링이 명단을 바꿨을 때 나가는 `roster_synced`가 담당한다
   - **전용 이벤트를 새로 만들지 않는다 (2026-08-09 결정)**: 확정 결과는 카운트라 저장되지 않고(처리 2·5), 화면에 새로 보일 값이 없다. BAT-002와 같은 이유다
5. 이후 해당 강의의 퇴실 창(`T_out−30 ~ T_out+60`) 동안 카메라 탐지·문자 플로우가 이 대상을 기준으로 동작

#### 대상 데이터

| 입력 | 출력 | 예상 건수 |
|---|---|---|
| `daily_roster` 해당 강의 잔존자 + LMS 최신 스냅샷 | 관리 대상 확정 + `attendance_exceptions` 자동 등록 | 강의당 수~수십 명 / 자동 등록 0~수 명 |

#### 실패 / 예외 처리

- **재시도**: LMS 호출 실패 시 3회, 1분 간격. 최종 실패해도 **BAT-001의 상시 폴링이 계속 돌기 때문에 판정 자체는 마지막 동기화 데이터로 진행** (확정만 지연)

- **중복 실행 방지**: 자동 등록은 `(date, student_id, type)` unique 기준 **멱등 upsert** — 재실행해도 409가 아니라 무변경 (API-005의 수동 등록 409 규칙과 다름, 아래 비고)
- **알림**: 최종 실패 시 ERROR 로그 (채널 ❓ 미결정 — 0장 공통 규칙 따름)

#### 실행 이력 기록
- `batch_runs`에 강의별 기록 (시각·강의 ID·관리 대상 수·자동 등록 수)

#### 비고
- **자동 등록과 수동 등록의 구분**: `attendance_exceptions.source` = `MANUAL`(행정실 등록, API-005) / `LMS_AUTO`(이 배치). 같은 학생·같은 유형이 이미 수동 등록돼 있으면 **수동 등록을 우선 보존**하고 자동 등록은 skip한다 (행정실이 적어둔 사유를 덮어쓰지 않기 위함)
- `LMS_AUTO` 예외는 SCR-003 목록에서 **삭제 불가로 표시**한다 — 삭제해도 다음 실행에 다시 생기고, 원천은 LMS 태그이기 때문 (API-007 비고 참조)
- 이 배치는 **문자를 보내지 않는다** — 문자는 카메라 포착 시점에 발송 직전 최종 확인을 거쳐 나간다 (rules/05 안전장치)
