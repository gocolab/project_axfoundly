## 2. 모델 선택

### 모델 및 실행 방식
- 상태: ✅ 확정 (2026-08-11 팀회의 — 얼굴 파이프라인 5종)
- 결정 — **얼굴 파이프라인 5종 (역할별)**:

  | 역할 | 모델 | 실행 위치 | 비고 |
  |---|---|---|---|
  | 탐지 | **YuNet** | **카메라(Jetson Nano) 탑재** | 얼굴 위치만. 경량 |
  | 식별(앙상블) | **ArcFace-R50 + AdaFace-ir101** | **GPU 서버** | 진짜 식별자는 이 둘 (실측 상위) |
  | 정렬·포즈 | **MediaPipe** (468점) | GPU 서버 | 식별 아님 — 정렬/각도 측정 보조 |
  | 정면화 | **TP-GAN** | GPU 서버 | 식별 아님 — 고도화(다음 주)·검증 후 도입 |

  - **⚠ "식별 모델"은 실제로 ArcFace-R50 + AdaFace-ir101 2개다.** MediaPipe(포즈)·TP-GAN(정면화)은 임베딩을 만들지 않으므로 식별자가 아니라 전처리 보조. "5종=4식별"이 아님.
  - **결합 방식**: ✅ **score fusion 확정** (2026-08-11 실측 — fusion=voting 동률이나, 확정 앙상블이 2모델이라 voting은 1:1 동점이 잦아 무의미. fusion이 모델 수 변화에 유연·단순. 아래 3장 결합 방식 실측)
  - **추론 환경**: 탐지=Jetson, 식별 앙상블=학원 GPU 서버. Jetson은 무거운 앙상블을 지지 못하므로 역할 분리
  - **⚠ 라이선스**: ArcFace-R50·AdaFace-ir101 **둘 다 비상업 연구 전용**(insightface/AdaFace 사전학습 모델). 학원 발표·포트폴리오는 무방, 실서비스는 재검토. SFace(Apache-2.0)는 고각 저하로 제외되며 상업 가능성도 함께 잃음
  - **LLM**: ✅ **gemma4:26b 확정** (2026-08-10) — 학원 GPU 서버 Ollama 구동. 툴콜·한국어·범위 밖 방어 실측 통과(VRAM 19/46GB, 응답 2초 내). qwen3는 한국어 질의 중 중국어 누출로 제외 (specs/14 6장)
- 결정일: 2026-08-05 (비전 툴 08-06 → 앙상블 확정 2026-08-11)

### 얼굴 식별(누구인지 판단)·라벨링 방식
- 상태: ✅ **확정 (2026-08-11) — 앙상블 ArcFace-R50 + AdaFace-ir101** (아래 3차 실측 근거)
- 결정: **탐지 YuNet + 식별 앙상블(ArcFace-R50 + AdaFace-ir101) + 동의자 사전 등록·코사인 유사도 매칭**

- **3차 실측 (2026-08-11 — 모델 5종 후보 + 앙상블, 세션 분리 9~10명)**:

  | 모델(단일) | top-1 | 분리도 | 라이선스 |
  |---|---|---|---|
  | ArcFace-R50 | **94.9%** | +0.463 | 비상업 |
  | AdaFace-ir101 | **94.9%** | **+0.492** | 비상업 |
  | ArcFace-R100(glint) | 93.8% | +0.505 | 비상업 |
  | AdaFace-ir50 | 91.5% | +0.412 | 비상업 |
  | SFace | 89.8% | +0.372 | Apache(상업) |

  | 앙상블(score fusion) | top-1 |
  |---|---|
  | AdaFace-ir101 + R50 | 94.9% |
  | AdaFace-ir101 + R50 + R100 | **95.5%** |

  - **팀이 지목한 "AdaFace 고각 강함"이 실측으로 확인됨** — 단, **ir101 기준**(ir50은 91.5%로 낮음). 백본 버전이 3.4%p를 가른다.
  - **앙상블은 단일 대비 +0.6%p** — 여러 모델이 다른 실수를 상쇄.

- **결합 방식 실측 (2026-08-11 — score fusion vs voting, 세션 분리)**:

  | 조합 | 단일 최고 | score fusion | voting |
  |---|---|---|---|
  | R50 + AdaFace-ir101 | 94.9% | 94.9% | 94.9% |
  | R50 + AdaFace + R100 | 94.9% | 95.5% | 95.5% |

  - **정확도로는 fusion=voting 동률.** 선택 기준은 운영성. **확정 앙상블이 2모델**이라 voting은 1위가 1:1로 갈려 사실상 fusion과 같아진다(홀수 모델에서만 voting이 자연스러움).
  - **→ score fusion 확정.** 유사도 z정규화 후 합산 → argmax. 모델 추가·제거에 코드 불변이라 유연.

- **가이드 등록 재측정 (2026-08-11 — 상/하 포즈가 CCTV 하향각 매칭을 돕는가, ArcFace 5인)**:

  | 등록 전략 | top-1 |
  |---|---|
  | 정면만 | 92.6% |
  | 전체 포즈(상/하 포함) | 93.8% |
  | **하향각 정합 등록** | **94.3%** |

  - **강사 방식(다각도 등록)이 실제로 개선** — 정면만 대비 **+1.7%p**. 지금까지 시도 중 **정면 등록의 한계를 넘은 첫 결과**(데이터 추가·앙상블은 미미, 3D 정면화는 -4%p).
  - ⚠ **효과가 작게 나온 이유 = 이 데이터의 CCTV 하향각이 약함** (pitch 중앙 CCTV 0.58 ≈ 등록 0.57, 분포 거의 겹침). **실제 설치 각도가 가파르면 이점이 더 커질 것.**
  - **→ 가이드 등록 UI에 위/아래 포즈 필수 포함**, 실제 카메라 설치 후 재측정으로 진짜 이득 확인.
  - ⚠ pitch는 5점 랜드마크 프록시(방향 판단용). MediaPipe 468점이면 더 정밀.

  - ⚠ **94~95%가 천장** — 남은 지렛대는 모델이 아니라 **촬영 조건(각도·해상도)**. 가이드 등록(상/하)이 그 조건을 등록 쪽에서 일부 보완하는 유일한 플러스 방향.
  - ⚠ 위 수치는 모두 **5~10명 폐쇄집합** — 실제 76명이면 하락. 방향 판단용.
  - ⚠ 수치는 **9~10명 폐쇄집합** — 실제 76명이면 하락. 방향 판단용.

- **[역사] 2026-08-06~07 SFace 검증 경과** (아래는 이력 보존 — 현재 선택은 위 앙상블):
  - 08-06 1차 94.8%는 같은 영상 연속 프레임을 등록/평가로 나눈 과대평가 → 08-07 세션 분리 재측정 27.1%로 무효화. SFace는 고각에서 저하가 커 앙상블에서 제외됨.
- ⚠️ **2026-08-07 재검증 결과 — 임계값 0.41 무효, 현재 촬영 조건에서 식별 실용 불가** (2차 실측 참조)
  - 선정 이유 중 **③ 정확도 항목은 측정 방식 오류로 무효화**됐다. 1차의 94.8%는 같은 영상의 연속 프레임을 등록/평가로 나눈 값이라 실제 운영 조건(다른 날 등록 → 다른 날 식별)을 반영하지 못했다. 세션을 분리해 다시 재면 **27.1%**다
  - ①라이선스 ②속도 ④운영 단순성은 그대로 유효하다. **SFace 선정 자체를 뒤집을 근거는 아직 없다** — ArcFace를 같은 세션 분리 조건으로 재측정한 적이 없기 때문. 모델 교체로 해결될 문제인지부터 확인해야 한다
    1. **라이선스**: SFace=Apache-2.0으로 시연·포트폴리오 활용에 제약 없음 (ArcFace buffalo_l은 비상업 연구 전용)
    2. **속도**: CPU 6.4ms/장 (ArcFace 52ms의 1/8) — GPU 서버 미확보 상태에서도 카메라 3대 실시간 처리·시연 보장
    3. ~~**정확도**: 등록 규칙 전제 시 실용 충분(94.8%)~~ → **무효 (2026-08-07)**. 세션 분리 시 27.1%
    4. **운영 단순성**: OpenCV 단독 의존 (onnxruntime·insightface 모델 관리 불필요), webapp FaceEngine에 이미 구현·E2E 검증 완료
  - 리스크 관리: FaceEngine이 어댑터 구조라 ArcFace 전환은 webapp 내부 설정 교체로 가능 — API-009 계약·backend는 모델 무관
- 방식: 동의자 사전 등록 + 임베딩 유사도 매칭 (후보 툴 공통 표준 방식)
- 조사 결과 (2026-08-05):
  - 후보안(사전 등록 + 임베딩 유사도 매칭)이 **후보 툴 전체의 공통 표준 방식**임을 확인 — 툴 선정과 무관하게 파이프라인 구조 동일
  - 라벨링은 용도별 2종: ① **식별 등록용 = 라벨링 도구 불필요** (`폴더명=사람` 구조가 라벨, 인당 3~10장) ② **탐지 mAP 평가셋(1,000장 요건)용 = 바운딩박스 라벨링 필요** (CVAT 웹 기반 팀 분담 권장, YOLO/VOC 포맷으로 3팀 호환)
  - 후보 3종은 층위가 섞여 있어 **탐지기(SCRFD/MTCNN/YuNet) vs 식별기(ArcFace/FaceNet) 분리 평가** 필요 — "Face Detection"은 탐지 전용이라 식별 불가
  - ⚠ 라이선스: insightface 사전학습 모델(buffalo_l)은 **비상업 연구 전용**(학원 데모·포트폴리오는 가능, 실서비스 확장 시 별도 라이선스). facenet-pytorch는 MIT
  - 임베딩 저장소는 MongoDB `registered_faces` 컬렉션(FastAPI 소유) 제안 — 04 파기 정책과 부합
  - 비교 테스트 환경: `debug/face_tool_comparison/` (bench_detect·bench_recognize·capture, RTX 4060 로컬)

  | 0.50 | 7.3% | 3.4% | 89.3% |
  | 0.55 | 3.4% | 0.6% | 96.0% |

  **→ 사용 가능한 임계값이 존재하지 않는다.** 낮추면 절반이 오매칭(0.30에서 43.5%), 높이면 대부분 미매칭(0.50에서 89.3%).

  **근본 원인 — 클래스 간 거리 < 클래스 내 거리**: 임계값 문제가 아니라 임베딩 분리도 자체가 무너져 있다.

  | 항목 | 값 |
  |---|---|
  | 다른 사람인데 임계 초과 | 유주성↔최진영 **0.524**, 유주성↔한소망 0.451, 김도윤↔황서범 0.414 |
  | 같은 사람 내부 평균 | 최진영 0.345, 김도윤 0.370, 유주성 0.472 |
  | 같은 사람·다른 세션 최저 | 민선아 **0.161**, 윤혜진 0.191, 박무현 0.268 |

  "다른 사람끼리 닮은 정도(0.52)"가 "같은 사람끼리 닮은 정도(0.35)"보다 크다 — 이 상태에서는 어떤 임계값도 성립하지 않는다.

  **원인 분석**: 데이터 부족이 아니라 **촬영 조건**으로 보인다.
  - CCTV 하향 각도 — 천장에서 내려다봐 정면 얼굴이 거의 없다. SFace는 정면 정렬 전제로 학습된 모델이다
  - 해상도 — 10편 중 5편이 640×480. 크롭 중간 크기 110~162px로 SFace 입력(112px)을 겨우 넘긴다
  - 참고: 저해상도 5편의 **얼굴 검출률이 오히려 65~85%로 1080p(14~29%)보다 훨씬 높았다** — 촬영 거리가 가까웠기 때문. 즉 "검출"은 되지만 "식별"이 안 되는 상태

  **선택지 (CTO 판단 대기)**:
  1. **카메라 각도 하향 조정 후 재촬영** — 근본 대응. 얼굴 높이에 가깝게 설치
  2. **등록용 정면 사진 별도 촬영** — CCTV로 등록부까지 만들지 않고 동의자 정면 사진으로 등록 (일반적인 얼굴인식 운영 방식)
  3. **ArcFace 동일 조건 재측정** — 각도 강건성이 나을 가능성. 단 비상업 라이선스 제약
  4. **시연 범위 조정** — 식별 대신 "사람 감지"까지만. LMS 태그가 primary이므로 구조상 성립 (rules/05 안전장치)

  **⚠ 이 결과가 확정될 때까지 `MATCH_THRESHOLD=0.41`(.env·webapp config)은 "임시값"으로 취급한다.** 그 값으로 운영하면 절반 이상을 놓치고 17.5%는 엉뚱한 사람으로 매칭한다

- 결정일: 2026-08-06 (툴 선정) / 2026-08-07 (정확도 근거 무효화·재검토 착수)

- 결정: **카메라 단독 판정으로 불이익 조치 금지** — LMS primary 원칙. SMS(복귀 요청)는 "퇴실 미체크(DB 잔존) AND 퇴실 시간대 영상 식별 포착" 이중 조건 충족 시에만 RPA로 발송(2026-08-05 조건 정정 — 99 참조). LLM이 발송 대상을 판단해도 발송 전 조건 검증 로직 통과 필수
- **발송 모드 스위치 (2026-08-07 추가 — 오발송 방지의 1차 방어선)**: `.env`의 `SMS_MODE`로 실발송 여부를 통제한다.
  - `test`(**기본값**): 수신자를 실제 학생이 아니라 **`SMS_TEST_RECIPIENT`(팀원 번호)로 강제 치환**하고, 본문 앞에 `[TEST]`를 붙인다. 판정·발송 흐름은 그대로 돌아가므로 개발·시연에 지장이 없다
  - `live`: `daily_roster.phone`의 실제 수신자에게 발송
  - ⚠ **`live` 전환 조건 2가지** — ① LMS 응답에 연락처가 실제로 들어오는 것을 확인 ② CTO 승인. LMS가 나중에 연락처를 채워주기로 했으므로(rules/04), 이 스위치가 없으면 **어느 날 갑자기 실제 학생에게 문자가 나가는 사고**가 난다
  - 기본값을 `test`로 두는 것이 핵심이다 — 설정을 잊었을 때 안전한 쪽으로 실패해야 한다
- **발송 직전 최종 확인 (2026-08-07 추가)**: 카메라 포착으로 발송 대상이 확정돼도, **문자를 보내기 직전에 LMS를 1회 재조회해 퇴실 여부를 최종 확인**한 뒤 발송한다. 폴링 주기(최대 1분) 사이에 정상 퇴실 태그가 찍힌 사람에게 복귀 문자가 나가는 오발송을 원천 차단하기 위함 — 실측상 정상 퇴실 태그가 수업 종료 이후에도 계속 찍힌다(specs/12 BAT-001 실측). 문자는 하루 몇 건이라 호출 부담이 없고, 이 장치 덕에 폴링 주기를 완화해도 안전하다
