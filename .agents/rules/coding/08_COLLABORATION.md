## 1. Git 규칙

### 브랜치 전략
- 상태: ✅ 결정
- 선택지: main 단일 / GitHub Flow / Git Flow
- 결정: GitHub Flow (feature branch 기반 개발 및 main/feature 연동)
- 이유: 에이전틱 개발 및 빠른 반복 주기와 기능 단위 배포에 최적화
- 결정일: 2026-08-24

### 커밋 컨벤션
- 상태: ✅ 결정
- 선택지: 자유 형식 / Conventional Commits / 한국어 요약
- 결정: Conventional Commits + 명확한 작업 요약
- 형식: `<type>(<scope>): <subject>` (예: `feat(course): 강의 등록 모달 및 API 연동`, `fix(auth): 토큰 갱신 로직 수정`)
- 허용 타입:
  - `feat`: 새로운 기능 추가
  - `fix`: 버그 수정
  - `docs`: 문서 및 명세 수정 (`specs/*`, `coding/*` 등)
  - `style`: 코드 포맷팅, 세미콜론 누락 등 (비즈니스 로직 변경 없음)
  - `refactor`: 코드 리팩토링 (기능 변경 없음)
  - `test`: 테스트 코드 추가 및 수정
  - `chore`: 빌드 업무 수정, 패키지 매니저 설정 등
- 이유: 변경 이력 추적성 및 자동 릴리즈/문서화 지원
- 결정일: 2026-08-24

### PR / 코드 리뷰 및 자동 동기화(하네스) 규칙
- 상태: ✅ 결정
- 결정: 하네스 파이프라인 연동 사전 Pull, 자동 Commit 및 **사용자 승인 후 Push**
  1. **작업 전 Pull**: `git status` 확인 후 `git pull origin <branch>`로 최신 원격 변경 반영
  2. **검증 완료 후 Commit**: 빌드/린트/테스트/문서동기화 품질 게이트 통과 후 즉시 로컬 커밋 (`feat:`, `fix:` 등 Conventional Commits 준수)
  3. **사용자 승인 후 Push**: 커밋 완료 후 사용자에게 커밋 내역(해시/메시지/브랜치)을 제시하고 명시적 승인을 확인한 후 `git push origin <branch>` 수행
  4. **충돌 방지**: force push 금지, 충돌 발생 시 즉시 감지 후 사용자 보고 및 병합
- 결정일: 2026-08-25 (수정)
